# 48 小時預報引擎驗證報告

> 由 `python -m services.forecast.run --verify` 自動產生。
> 對應架構書預報層、構想書議題三。**本報告的結論不利之處一律照實呈現。**

## 方法

- **滾動起報（rolling origin）**：訓練集永遠在測試集之前，中間留 7 天 gap。
  gap 的用意是避免同一場地磁暴前半段在訓練、後半段在測試——那等於偷看答案。
- **同一擂台**：所有模型用同一測試集、同一真值、同一操作點，數值可橫向比較。
  （方法論移植自 Sat_TraingDataExtension/three_layer_common_eval.py）
- **Tier 0 門檻**：ML 模型必須贏過持續性、氣候平均、27 日復現三個基線才准上線。
- **信賴區間**：MAE 附 bootstrap 95% CI，不報單一數字。

### 事件與時間標籤定義

- **事件**：Kp ≥ 5（G1 以上），基率約 3%
- **樣本單位**：每個 3 小時 Kp 區間為一筆；時間標籤採該區間的**起始時刻**
- **對齊**：預報值與觀測值使用相同時間標籤，於目標時刻**逐點比對**，
  未設 ±時間容差窗（比容差版嚴格，POD 因而偏低）
- **POD** = 命中 ÷ 實際事件數；**FAR** = 誤報 ÷ 所有發報數
- **操作點**：機率門檻在**訓練折**上選定（預設最大化 CSI），
  不得用測試折挑門檻。報表同列 `POD_train` 與 `POD` 以顯示轉移落差。

## 結論與限制（必須隨數字一併呈現）

1. **短 horizon 有技巧，長 horizon 沒有。** 3、6、12、24 小時四個 horizon 上
   ML 模型贏過最佳基線約 2–8%；48 小時**氣候平均勝出**，ML 未能超越，
   依 Tier 0 門檻不應上線。

2. **未達構想書的 KPI。** 構想書訂 POD ≥ 0.7、FAR ≤ 0.4，實測全部未達標，
   且 24 小時的 BSS 已轉負（機率產品不優於「永遠報氣候頻率」）。

   改用 `--objective pod` 後，**訓練折可達 POD 0.728，但測試折僅 0.064**。
   機率分布在折間漂移，目標型操作點沒有外推能力。程式會主動標示此落差，
   不可依訓練折的達標宣稱滿足 KPI。

3. **未與官方預報比較。** 真正的對手是 NOAA SWPC 官方 3 日預報（已介接
   `swpc_geomag_forecast`），但 SWPC 只發布當前一份、取不到歷史版本，
   故無法回測比較，只能自累積之日起做前瞻比較。
   **在累積足夠樣本前，不應宣稱本引擎優於官方預報。**

4. **長 horizon 表現不佳的歸因不宜過度簡化。** L1 太陽風僅約 30–60 分鐘先導期
   確實是硬限制，但本結果同時受以下條件約束，不足以斷言「不可能有技巧」：
   - 只試過梯度提升樹單一模型族
   - 目標選 Kp，而非動力學較平滑、且直接驅動熱氣層密度的 Dst
   - 事件基率僅約 3%，正樣本稀少
   - **完全沒有 CME 到達時間資訊**——這是 24–48 小時預報的主要缺口

5. **可能的改進方向**（尚未實作）：以 Dst 為目標、引入 CME 到達時間模型、
   集合預報以離散度表達不確定度、分別針對「事件發生」與「事件強度」建模。
